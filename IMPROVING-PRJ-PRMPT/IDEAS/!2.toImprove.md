# Handoff: avoid mb-lint / mb-doctor policy drift during task 3

## Status

Do not fix this as a standalone refactor.

Treat it as an opportunistic cleanup only while implementing task 3
(`T2` no per-task red-verify; `T3` keeps per-task red-verify; `T2` gets
feature-level red-verify after feature implementation).

## Real problem

`mb-lint.mjs` and `mb-doctor.mjs` are separate tools with separate roles:

- `mb-lint.mjs`: structural/mechanical validation;
- `mb-doctor.mjs`: autonomous/readiness policy gate.

The duplication is only a real risk where both tools encode the same policy
surface and task 3 changes that surface.

For task 3, the likely drift risk is around:

- task tiers: `T0|T1|T2|T3`;
- full-protocol tiers: currently `T2|T3`;
- red-verify closure policy: should become per-task `T3` only;
- exact semantic-pass marker;
- T3 human/recovery markers;
- possibly shared task/status constants if touched by the task 3 fix.

## KISS rule

Do not extract a broad helper module just because code is duplicated.

Only extract shared code if task 3 requires changing the same constant/helper in
both `mb-lint.mjs` and `mb-doctor.mjs`.

If only `mb-doctor.mjs` changes for task 3, leave `mb-lint.mjs` alone.

## Optional minimal extraction

If task 3 touches both files and duplicated policy constants would otherwise
need parallel edits, create:

```text
skills/mb-garden/assets/mb-common.mjs
```

Keep it tiny. Suggested maximum contents:

- `TASK_STATUSES`
- `TASK_TIERS`
- `FULL_PROTOCOL_TIERS`
- `PER_TASK_RED_VERIFY_TIERS`
- `RED_VERIFY_PASS_RE`
- `T3_HUMAN_CHECKPOINT_MARKER`
- `T3_ROLLBACK_RECOVERY_MARKER`
- `TASK_ID_RE`
- `canonicalPacketRef(taskId)` only if both tools already need it in touched
  code

Do not extract:

- `errors.push(...)` behavior;
- `addFinding(...)` behavior;
- JSON/read helpers;
- path walking;
- CLI parsing;
- `ROOT` / `process.cwd()`;
- `spawnSync`;
- severity/strict-mode logic.

## Bootstrap impact if `mb-common.mjs` is added

Only if the file is actually created:

1. Add it to `skills/_shared/scripts/init-mb.js` `RUNTIME_SCRIPT_ASSETS` before
   `mb-lint.mjs` and `mb-doctor.mjs`.
2. Make `mb-lint.mjs` / `mb-doctor.mjs` import it as:

```js
import { ... } from './mb-common.mjs';
```

3. Update release-check to assert fresh targets contain
   `scripts/mb-common.mjs`.

## Acceptance criteria

- Task 3 policy is not duplicated inconsistently between `mb-lint.mjs` and
  `mb-doctor.mjs`.
- No broad shared helper layer is introduced unless both tools genuinely need
  the same touched policy constants.
- If `mb-common.mjs` is introduced, fresh bootstrap copies it and both tools run
  from target `scripts/`.
- Existing lint/doctor behavior remains unchanged except for the explicit task
  3 red-verify policy change.
- Source-only hygiene remains clean:
  `find skills -path 'skills/_shared' -prune -o -type f -name 'shared-*' -print | wc -l`
  returns `0`.
